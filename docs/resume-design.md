# 分段落盘与断点续传恢复（T5）

实现：`internal/engine/sink/`（`file.go` 落盘、`resume.go` 恢复决策、`saver.go` 顺序保证）。
上游写入方为 `internal/engine/httpdl`，元数据由 `internal/store` 持久化。

---

## 1. 一致性约定（最重要的一条）

```
写数据(WriteAt) → 位图标记(内存) → fsync 数据文件(Sync) → 元数据原子落盘(Store.Save)
```

`ProgressSaver.Save` 强制了「先 fsync 数据、再写元数据」的顺序。由此得到两条保证：

| 事实 | 结论 |
|---|---|
| 元数据里的位图声称某块已完成 | 该块数据**一定**已经到达磁盘 |
| 进程在任意点被强杀 | 最坏结果是「数据已落盘但位图未记录」，重启后重下该块 |

反过来的顺序（先写元数据后落数据）会在断电时留下「位图声称完成、磁盘上是空洞」的坏文件。
这是本设计要排除的头号错误。

---

## 2. 落盘：`FileSink`

```
最终文件:  D:\downloads\blob.iso
临时文件:  D:\downloads\.blob.iso.p2pdl.part     ← TempPathFor("D:\downloads\blob.iso")
```

- **不用整文件预分配**（T1 §6 风险 4）：空洞由位图管理，文件按 `WriteAt` 自动向后扩展。
  好处是 10GB 文件在 0.1% 进度时不会先占满磁盘，也不会在 Windows 上触发昂贵的预分配。
- **临时文件与最终文件同目录**：保证 `os.Rename` 在同一卷内完成，从而具备原子性
  （跨卷 rename 会退化为复制 + 删除）。
- **`Commit` 顺序**：`Sync → Truncate(TotalSize) → Sync → Close → Rename`。
  `Truncate` 用于修正长度，防止尾部残留多余数据；`Rename` 保证最终文件要么不存在、要么完整。
- **`Close` vs `Commit`**：暂停/取消时用 `Close`（保留临时文件以便续传），
  完成时用 `Commit`，放弃任务时用 `Discard`（删除临时文件）。
- **周期 fsync**：默认每写入 8MB（`DefaultSyncInterval`）主动 fsync 一次，
  在「强杀后重下的量」与「系统调用开销」之间取平衡。

---

## 3. 恢复决策：`PlanRecovery`

判定原则是**宁可重下，不可续错**：

| 条件 | 决策 | 理由 |
|---|---|---|
| 元数据 `Validate()` 失败 | `restart` | 分片区间可能重叠或空洞，位置不可信 |
| `TotalSize <= 0`（长度未知，单流模式） | `restart` | 无法向服务端定位任意偏移，续传无意义 |
| 位图有声明的进度，但临时文件不存在 | `restart` | 数据与进度不一致 |
| 临时文件长度 < 位图声称的最高偏移 | `restart` | 文件被截断/被外部修改，续写会留下空洞 |
| 临时文件长度 ≥ 声称偏移（可更长） | `resume` | 多余尾部会在 `Commit` 时被截断 |
| 数据已齐全 | `resume`（无缺口） | 交由 T9 做完整性校验后提交 |

`restart` 不是错误路径，而是安全兜底：调用方应删除临时文件并重建任务。

---

## 4. 缺口计算：`MissingRanges` / `MergeRanges`

缺口由位图的 `Gaps()` 推导，**不是**由「已下载字节数」推导——后者无法表达碎片位置。

```
每个分片: Bitmap.Gaps() → 相对分块区间 → 换算为绝对字节区间
所有分片缺口 → 排序 → 合并重叠与相接区间 → 结果互不重叠、按起点升序
```

`MergeRanges` 是「重复恢复多次不产生区间重叠或空洞」的落点：
- 相接区间（`r.Start == last.End`）会被合并，不会出现重复下载的边界块；
- 交叉/包含关系会被吸收，不会产生负长度区间；
- 空区间被丢弃。

不变式（有测试保证）：`sum(MissingRanges) + task.Downloaded() == task.TotalSize`。

## 5. 端到端验证

`internal/engine/sink/e2e_test.go` 用「支持 Range 的慢速服务器 + 真实文件 + 真实元数据存储」验证：

1. 2MB 内容、4 分片、并发 2；每轮下载 80ms 后调用 `context.Cancel` 制造中断；
2. **每轮开始都从磁盘重新 `Load` 任务**（模拟进程重启），而不是复用内存状态；
3. 每轮都用 `PlanRecovery` 决策，断言必须为 `resume` 而非 `restart`；
4. 最终文件长度、`bytes.Equal` 与 **SHA-256 三重校验**。

若区间出现重叠，文件会出现重复内容；若出现空洞，文件会出现零填充——两者都会让 SHA-256 不匹配。
因此**哈希一致即同时证明了「无重叠」与「无空洞」**。

## 6. 已知边界

| 场景 | 行为 | 说明 |
|---|---|---|
| 源不支持 Range | 无法续传 | 单流模式下重启即重下，属协议能力限制（T4 已降级而非报错） |
| 内容被远端修改（大小/ETag 变化） | 需上层判定后 `restart` | 上游应在恢复前比对 `ETag`/`Last-Modified`（T8/T9 接线） |
| 临时文件被外部程序截断 | `restart` | 由「文件长度 < 声称偏移」检出 |
| 磁盘空间不足 | 写入返回错误并进入重试 | 预检查在 T6 加入 |
